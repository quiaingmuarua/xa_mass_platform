30-second mental model

先记住四件事

项目的大部分设计都可以从下面四个判断推导出来。

1

Task 是调度容器

它承载稳定意图、TaskType、WorkerGroup 和调度配置，不是一次执行尝试。

2

TaskItem 是唯一工作单元

从 append、claim、dispatch、retry 到 finality，始终是同一个 messageId。

3

WorkerId 是一个执行槽

一个 WorkerId 同时只拥有一个活动租约；物理并发用多个逻辑 WorkerId 表达。

4

Score 是调度真相

Score 决定何时值得观察；descriptor、payload、result、transport 不会被塞进 Score。

最重要的边界：Score 不是资源写锁，也不是完整状态对象。资源 owner 写资源真相；调度 plane 只移动自己的调度坐标。

Mainline

一条主链，四个调度平面

没有第二条兼容路径，也不靠外部事件维持普通正确性。每一步只产生下一位 owner 所需的最小证据。

ADMISSION 中的 timeSlot 与 priority

timeSlot 决定 bounded observation window；窗口成员再按 suffix priority 排序。未 transition 的已观察 Task 会被放到未来 recheck time，避免旧 head 永久遮住后续工作，但 priority 本身不会被内核降低。

Evidence convergence

结果不是回调逻辑，而是 Owner 收敛

SeedResultRuntime 只做三类 outcome queue；ResultRoutingPacer 解码一次，再把 Task evidence 与 Worker evidence 分开交给真实 owner。

SUCCESS

  • Item → FINAL_SUCCESS
  • 精确释放 Worker lease

WORKER_FAILURE

outcomeCode = 1xxx
  • 精确释放 Worker lease

outcomeCode = 3xxx
  • Worker lease → RECOVERY_RECHECK
  • 不直接写 Item retry

为什么 CandidateWorkerCache 不是生命周期真相？

它只保存 TASK_DRIVEN 的短期预计算 Worker evidence。miss、stale 或过期只会让本轮没有候选；Task、Item 和 Worker 的真实状态仍由各自 owner 与 Score 轴决定。

为什么 Worker failure 不直接把 Item 写回 ready？

Item claim 本身已经写入未来 lease coordinate。Worker failure 只释放 Worker；到期后的 Item 会被普通 TaskItem acquisition 再次观察，避免 Result Routing 成为第二个 retry owner。

为什么不靠 append/result 事件唤醒调度？

高频事件容易产生放大和第二套 liveness。当前设计允许事件做有损加速，但 correctness 必须由 bounded score scan、lease expiry 与 owner-local recheck 自行收敛。
