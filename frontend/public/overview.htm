XA Mass
架构全景

XA Mass 将大量任务项交给明确的 Worker 执行。Kernel 负责调度与收敛， Matching 解释 Worker 事实与匹配规则，Server 提供统一访问与装配， Transport 负责投递和本地执行。任务进度、连接状态与结果分别由对应 Owner 维护， 调用方通过公开 API 提交工作并观察它们的关系。

Architecture Entry Java Kernel Proof Lanes

01 · Authority

清晰的决策、服务与执行边界

每个 Owner 维护自己的事实，跨模块传递有界证据。Matching 独立维护 Properties 和规则解释；Server 组合这些 Owner 的能力，调度决定仍由 Kernel 作出。

KERNEL

Decide & converge

维护 Task、TaskItem 与 Worker 的调度状态，决定资源分配、重试、恢复和最终状态。

SERVER

Expose & route

校验公开请求，维护身份与绑定，装配 Owner，并关联调用及结果。

ADAPTER

Deliver

使用当前已验证路由投递 Command，接收 Report，并执行 Adapter 本地事件。

WORKER

Resolve & execute

按完整 Event Name 找到已装配的能力，执行本地 Handler，返回结果证据。

判断归属：资源选择、租约、任务项领取与重试属于 Kernel；Properties 和规则解释 属于 Matching；公开访问与请求关联属于 Server；当前连接、消息投递和本地事件执行 属于 Transport。观察到的结果不自动成为另一 Owner 的状态。
ASSIGNMENT DISPATCH

资源决策

组合有界资源证据与精确围栏，形成已经确定目标的 Command。

AUTHORITY ROUTING

消息owner路由

把 Command 交给对应 Adapter，把返回证据路由给负责解释它的 Owner。

EVENT DISPATCH

本地函数调用

Adapter 与 Worker 按目标和完整事件名调用本地 Handler。

02 · TASK mainline

从任务提交到结果观察

Task scheduling 是 Kernel 控制流主线。Server 与 Transport 消费调度结果，但不能反向更换 Worker 或决定 Item finality。

Task initialization
Task 经批准进入初始化，资源准备完成后进入常规调度。
Worker acquisition
PRECOMPUTED 由 Matching 解释规则并提供候选证据；ON_DEMAND 由 Kernel 按显式身份或有限选择指令获取 Worker。
Lease & claim
Kernel 精确确认 Worker 租约并领取 TaskItem，随后发布定向 Command。
Server routing
Server 暴露有界 Command 消费入口，不重新选择 Worker。
Transport
Adapter 经已验证路由投递，Worker 执行本地能力，并返回结果证据。
Result Routing
Kernel 将结果证据交给语义事件 Owner。Result 观察与 TaskItem 最终状态独立维护，跨 Owner 调用间仍存在失败窗口。
TaskDescriptor→ TaskItem→ Worker lease→ Item claim→ DeliveryCommand→ DeliveryReport→ owner transitions
TASK SCORE

Task scheduling visibility

维护 Task 在调度流程中的位置与可见性。

WORKER SCORE

Scheduling serviceability

表示调度可用性与下一次可获取时间；连接状态由 Adapter 独立观察。

TASKITEM SCORE

Claim, retry & finality

维护任务项领取、重试和最终状态。

03 · DIRECT_CALL

调用方明确指定目标

DIRECT_CALL 提供有限的直接调用与结果关联。调用方选择目标， Server 完成准入后，复用 Adapter 和 Worker 的投递执行路径。

Explicit target
调用方选择 Adapter，以及需要调用的 Worker 目标或 Adapter 本地事件。
Admission
Server 校验身份与绑定，只接受所属 Adapter 的有界请求。
Shared mailbox
Worker 直接调用只进入空闲邮箱；权威 TASK 投递仍可替换尚未消费的直接调用。
Unified delivery
DIRECT_CALL 与 TASK 共享 Transport 的连接、投递和本地事件执行机制。
Correlation
Server 在有界等待期间关联 SYSTEM 结果；超时仅表示本次观察未得到结果。
BEST EFFORT

明确不承诺

  • 不创建Task或TaskItem
  • 不进入Result Routing
  • 不创建独立可靠Command或Result存储
  • 不提供结果查询与可靠重试
  • 不提供pause、drain、互斥或抢占
  • 不允许Server从候选Worker中选择目标

直接调用采用 best-effort 语义。业务若需要可恢复执行或持续状态，应先定义相应的 Owner 契约。

04 · Transport substrate

共同机制，完整物理owner

Delivery Contract 定义跨平台协议；Adapter、Worker Core 与平台 Worker 分别维护投递、执行和物理网络资源。实现细节由各模块文档维护。

NETTY ADAPTER

投递与连接

Aggregate整体生命周期与关闭次序。
Connection身份验证、当前路由与有效结果入口。
Physical Server监听、连接、帧处理和物理读写。
WORKER CORE

显式运行与本地能力

Client物理网络与透明重连。
Transport身份协议、Command 解码、本地执行和 Result 编码。
Run Controller显式启动与停止；端点耗尽后由 Host 决定再次启动。
PREPARE & IDENTITY

Server拥有注册坐标

每次显式启动加载完整 Properties，并通过 Server Prepare 更新身份、绑定与事实。透明重连复用准备结果。

JAVA HOST

显式启动，共享平台资源

Host 管理有限 Worker 集合；Java 与 Android 平台分别拥有网络、执行器和重连资源。

SCENARIO LAB

Mutation source，不是真相源

文件、启动、停止与 checkpoint 建立本地动作证据；系统效果由 Adapter 和 Kernel 的公开观察独立确认。 

Command
  Kernel / Server -> Adapter -> current verified route -> Worker

Local execution
  complete Event Name -> assembled capability -> Handler

Result evidence
  Worker / Adapter -> Server -> semantic Owner

Contract details
  Delivery Contract / Server / Adapter / Worker Owner documents

05 · Runtime topology

一套 Java Kernel
两个稳定性层级

稳定机械 Owner、变化较快的调度策略与 Worker 匹配事实分别由独立模块维护。 Server 将它们装配为一个运行时，Worker Host 在外部运行。 发布包与本地实验 Host 有明确边界，Redis 由部署环境提供。

DOC / KERNEL

Authority index

Java Kernel总入口连接mechanical Owner、Pacer Policy、跨模块边界和对应proof，不复制第二份运行机制。

KERNEL_JVM

Mechanical owners

维护稳定机械契约、Score、资源和 Redis 转换。

KERNEL_PACER_JVM

Policy & lifecycle

维护生产调度策略、结果收敛与有限生命周期。

WORKER_MATCHING_JVM

Facts & rule interpretation

维护 Worker 事实与 PRECOMPUTED 规则，为 Kernel 提供有界候选证据。

SERVER_JVM

API & Spring assembly

装配 Kernel 与 Matching，提供公开 Runtime API，并管理应用生命周期。

TRANSPORT

Delivery mechanisms

提供共享协议、Worker Core、Adapter，以及 Java 和 Android 平台实现。

ASSEMBLY & OBSERVATION

Finite edges

Scenario 与 Android Host 装配具体能力；Integration 和 Frontend 通过公开 API 验证或观察系统。 

Runtime
  Server API and application assembly
    -> Kernel mechanical owners + production Pacer
    -> Worker Matching
    -> Adapter
    -> external Redis

Deployment
  Server Runtime ZIP -> Server + Pacer + Frontend
  Worker SDK ZIP     -> shared contract + Worker libraries

  Scenario Host      -> independent source-checkout Lab process

06 · Proof & stability

固定claim，分层证明

每个机制claim只有一个Primary Proof；其他lane只能提供前置条件或边界见证。 完美正确性、故障收敛、连接容量与Android进程事实不能互相替代。

STABLE CUT

稳定owner cut

  • Task、TaskItem、Worker三条独立score轴
  • PRECOMPUTED有序Demand与ON_DEMAND身份直选
  • 稳定机械 Owner 与生产策略分别维护
  • Kernel / Matching / Server / Transport 职责
  • Adapter 投递、Worker 执行与平台资源分别维护
  • Server发行包与Worker Host/SDK独立
EVOLVING

Owner-local增量

  • 有明确生产caller的mechanical operation
  • 有限Server use case
  • Worker Prepare与Host资源实现
  • Scenario / Android capability和Lab surface
  • deployment、projection与claim-owned proof
DEFERRED

独立未来路线

  • 分布式Pacer leader election与multi-active Kernel
  • 分布式DIRECT_CALL correlation
  • 认证、Adapter HA与显式unbind
  • persistent delivery ack
  • 大规模活跃Task公平、分片与Property Index
  • 通用plugin与动态Process系统

Owner & Boundary

JVM Contracts固定Owner算法与架构；Redis Owner证明原子转换；Runtime Boundary证明相邻Owner和协议拓扑。

Worker Correctness

Convergence Health

Worker Loaded Capacity + Recovery Stability

Android Worker Proof

Finite Product Lanes
