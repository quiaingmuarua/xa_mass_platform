XA Mass
架构全景

Kernel 决定谁应该执行什么；Server 负责外部访问、有限编排、authority routing 与请求相关性；Transport 把已经形成的 Command 送到目标，并调用 endpoint-local handler。三层都可以出现 dispatch，但只有 Kernel Assignment Dispatch 做资源决策。

Architecture Entry Kernel Oracle Proof Lanes

01 · Authority

一个系统，四个明确 owner

分层不是按技术栈，而是按谁能够维护 truth、谁只能携带 evidence。 Server 可以暂时复杂，但不能通过 use case 偷偷变成第二个 Kernel。

KERNEL

Decide & converge

Task、TaskItem、Worker scheduling truth，以及selection、lease、claim、retry、recovery和result disposition。

SERVER

Expose & route

API、validation、provider assembly、有限use-case编排、Identity、Binding、authority routing和waiter correlation。

ADAPTER

Deliver

批量Command/Report、当前Worker route、物理连接、Adapter-local handler。它不重新选择Worker。

WORKER

Resolve & execute

通过 (src, messageType) 找到静态Definition，执行resolver与handler，并生成Result evidence。

判断规则：如果逻辑在决定“Command 是否应该存在、什么时候执行、哪个 Worker 执行、是否重试”，它属于 Kernel；如果 Command 已经存在，只是在选 source、找 connection、调用 handler 或把 Result 交回 owner，它属于 Server / Transport。
ASSIGNMENT DISPATCH

资源决策

Kernel读取有界证据，完成Worker acquisition、lease、TaskItem exact claim，并产生already-targeted Command。

AUTHORITY ROUTING

消息owner路由

Server在已存在的TASK与CONTROL_ONLY authority之间选择一个source，并按Result destination分流。

EVENT DISPATCH

本地函数调用

Adapter或Worker根据目标与messageType调用本地handler，不读取Task priority或Worker score。

02 · TASK mainline

调度决定只形成一次

Task scheduling 是 Kernel 控制流主线。Server 与 Transport 消费调度结果，但不能反向更换 Worker 或决定 Item finality。

Kernel admission
Task score 提供调度域、时间坐标和lane状态；policy在bounded running limit与Task条件下执行合法transition。
Worker acquisition
TASK_DRIVEN 可复用Task级PRECOMPUTED candidates；ITEM_DRIVEN 在Item到来时DIRECT获取Worker。
Lease & claim
Worker score exact lease与TaskItem score exact claim共同接受一次assignment，随后写入Adapter分区Command mailbox。
Server routing
Server在当前Command authorities中选择一个source，向Adapter返回已经包含目标workerId的Command map。
Transport
Adapter通过当前verified route投递；Worker同步执行Definition并返回保留原始forward与payload的DeliveryReport。
Result Routing
TASK evidence进入Kernel Result Routing，由owner-local policy决定last-success、retry/finality与Worker disposition。
TaskDescriptor→ TaskItem→ Worker lease→ Item claim→ DeliveryCommand→ DeliveryReport→ owner transitions
TASK SCORE

Task scheduling visibility

调度band、下一次lane动作时间与owner-local suffix。它不镜像Worker资源。

WORKER SCORE

Scheduling serviceability

HOT/RECOVERY polarity、time、lane与dirty。它不是socket在线状态。

TASKITEM SCORE

Claim, retry & finality

ACTIVE预算与到期坐标、exact claim、retry和单调final promotion。

03 · CONTROL_ONLY

直接控制，不伪装成Task

调用方已经明确选择目标，因此Server无需重新调度。它只做bounded admission、 memory mailbox与结果相关性，并复用同一套Adapter delivery。

Explicit target
调用方在一个Adapter URL下提交同Group的1..100项workerId → opaquePayload；使用顶层opaquePayload时直接控制该Adapter。
Admission
Worker调用批量读取descriptor、pause score与Binding，并要求Binding等于URL中的Adapter；Server不会跨Adapter拆分调用。
Memory mailbox
每个Adapter、每个target一个未消费槽位，latest-write-wins；waiter与Server进程同生命周期。
Unified delivery
CONTROL_ONLY与TASK共用Adapter Command Process、Report Process、connection和Worker Dispatcher，不增加第二条Transport状态机。
Correlation
合法SYSTEM Result完成当前target；timeout、replace、shutdown与Result精确竞争。迟到、重复或不匹配证据被丢弃。
BEST EFFORT

明确不承诺

  • 不创建Task或TaskItem
  • 不进入Result Routing
  • 不持久化Command或Result
  • 不提供结果查询与可靠重试
  • 不把pause变成Worker mode字段
  • 不允许Server从候选Worker中选择目标

CONTROL_ONLY可以承载快速、pure-memory管理handler；需要解绑、迁移、排他维护或可靠执行时，应建立独立管理owner。

04 · Transport substrate

共同机制，完整物理owner

Adapter和Worker都采用三层owner。统一发生在稳定机制合同上；WebSocket、line Socket、 OkHttp与Android HandlerThread仍由具体物理实现完整拥有。

NETTY ADAPTER

三层冻结结构

AggregateAdapter lifecycle、Process Manager和network shutdown ordering。
ConnectionInbound callback adapter、identity、first verification、route registry、Command routing与Result ingress。
Physical Server完整WebSocket或line-Socket listener、EventLoop、全部Channel、framing、write与close。
WORKER CORE

三层运行结构

Client具体网络、透明重连和物理callback serialization。
Transportidentity、Command decode、同步handler execution、Result encode与endpoint termination。
Run Controller只拥有RUNNING/STOPPED与一次Preparation；不拥有connection或Command。
DeliveryCommand
  targetAddress outside DTO
  src + dst + messageType + deadline + payload + opaque forward

Adapter
  WORKER target  -> current verified Channel -> physical write
  ADAPTER target -> fixed local handler

Worker
  (src, messageType) -> immutable Definition -> resolver -> handler

DeliveryReport
  producer src + sourceId + destination + outcome + opaque payload/forward

05 · Runtime topology

一个机制oracle，增量生产装配

当前不是“Python版”和“Java版”两个Kernel。Python保存完整scheduling/application oracle；JVM只迁移有明确生产caller和parity proof的owner操作。

KERNEL_DESIGN

Mechanism oracle

Python executable spec、owner Redis provider、Pacers、Result Routing与Kernel application lifecycle。

KERNEL_JVM

Selected parity

Java 21 owner contracts与选定Redis providers。缺失operation显式失败，不提供scheduler fallback。

SERVER_JVM

Hybrid assembly

Spring API把Task control绑定到Python，把已迁移resource/data/delivery owner绑定到Java provider。

TRANSPORT

Delivery mechanisms

Java 11 contract/Core、Netty Adapter、Java Worker与Android Worker，不依赖Kernel调度实现。

CAPABILITIES

Finite assembly

Scenario Workers与Android capabilities提供具体Definitions和Host assembly，不建设通用插件系统。

OBSERVATION

Integration & frontend

外部acceptance、Runtime Viewer和Task Batch Lab只通过公开API证明或观察，不拥有运行truth。

真相分类：truthevidenceaddress correlationprojectionhint。 evidence、projection和hint不能因为“方便”而升级为调度或生命周期truth。
