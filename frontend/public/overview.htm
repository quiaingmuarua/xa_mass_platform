Current architecture · Java production kernel

XA Mass
架构全景

生产 Kernel 已完全由 Java owner 与固定 Pacer 组成。Kernel 决定谁应该执行什么； Server 负责外部访问、有限编排、authority routing 与请求相关性；Transport 把已经形成的 Command 送到目标，并调用 endpoint-local handler。三层都可以出现 dispatch，但只有 Kernel Assignment Dispatch 做资源决策。

Architecture Entry Java Kernel Proof Lanes

01 · Authority

一个系统，四个明确 owner

分层不是按技术栈，而是按谁能够维护 truth、谁只能携带 evidence。 Server 可以暂时复杂，但不能通过 use case 偷偷变成第二个 Kernel。

KERNEL

Decide & converge

Task、TaskItem、Worker scheduling truth，以及selection、lease、claim、retry、recovery和result disposition。

SERVER

Expose & route

API、validation、provider assembly、有限use-case编排、Identity、Binding、authority routing和waiter correlation。

ADAPTER

Deliver

批量Command/Report、当前Worker route、物理连接、Adapter-local handler。它不重新选择Worker。

WORKER

Resolve & execute

通过完整的 messageType Event Name 找到静态Definition，执行resolver与handler，并生成Result evidence；src只保留调用来源证据。

判断规则：如果逻辑在决定“Command 是否应该存在、什么时候执行、哪个 Worker 执行、是否重试”，它属于 Kernel；如果 Command 已经存在，只是在选 source、找 connection、调用 handler 或把 Result 交回 owner，它属于 Server / Transport。
ASSIGNMENT DISPATCH

资源决策

Kernel读取有界证据，完成Worker acquisition、lease、TaskItem exact claim，并产生already-targeted Command。

AUTHORITY ROUTING

消息owner路由

Server将Adapter Direct FIFO与共享Worker Command mailbox暴露给Adapter，并按Result destination分流。

EVENT DISPATCH

本地函数调用

Adapter或Worker根据目标与messageType调用本地handler，不读取Task priority或Worker score。

02 · TASK mainline

调度决定只形成一次

Task scheduling 是 Kernel 控制流主线。Server 与 Transport 消费调度结果，但不能反向更换 Worker 或决定 Item finality。

Task initialization
Task score 在approve时原子检查固定RUNNING容量，先进入INITIAL排序坐标；满足启动条件后才精确推进到NORMAL调度范围。
Worker acquisition
PRECOMPUTED_TASK_RULE 先预计算Task级候选、Dispatch再续租缓存候选；ON_DEMAND_ITEM_RULE 在Item调度时按需获取Worker。两者共用同一Matcher，Idle行为独立选择立即关闭或Kernel私有park。
Lease & claim
Worker score exact lease与TaskItem score exact claim共同接受一次assignment，随后写入Adapter分区Command mailbox。
Server routing
Server先读取Adapter Direct FIFO，再从共享Worker Command Hash消费一次，返回已经包含目标workerId的Command map。
Transport
Adapter通过当前verified route投递；Worker同步执行Definition并返回保留原始forward与payload的DeliveryReport。
Result Routing
TASK evidence进入Kernel Result Routing。SUCCESS先写Result查询投影，再分别请求TaskItem FINAL_SUCCESS与Worker lease释放；Result HASH不是Item finality truth，这些owner调用有顺序但不跨资源原子。
TaskDescriptor→ TaskItem→ Worker lease→ Item claim→ DeliveryCommand→ DeliveryReport→ owner transitions
TASK SCORE

Task scheduling visibility

调度band、下一次lane动作时间与owner-local suffix。它不镜像Worker资源。

WORKER SCORE

Scheduling serviceability

HOT/RECOVERY polarity、time、lane与dirty。它不是socket在线状态，也不承诺跨Evidence Batch的单调连接历史；后续Route或Probe证据驱动最终收敛。

TASKITEM SCORE

Claim, retry & finality

ACTIVE预算与到期坐标、exact claim、retry和单调final promotion。

03 · DIRECT_CALL

直接控制，不伪装成Task

调用方已经明确选择目标，因此Server无需重新调度。它只做bounded admission、 mailbox offer与结果相关性，并复用同一套Adapter delivery。

Explicit target
调用方在一个Adapter URL下提交同Group的1..100项workerId → opaquePayload；使用顶层opaquePayload时直接控制该Adapter。
Admission
Worker调用批量读取descriptor与Binding，并要求Binding等于URL中的Adapter；它不读取score，也不会跨Adapter拆分调用。
Shared mailbox
Worker Command通过HSETNX只填空槽；TASK append可在消费前覆盖它。Adapter Command进入Server内存FIFO，waiter与Server进程同生命周期。
Unified delivery
DIRECT_CALL与TASK共用Adapter Command Process、Report Process、connection和Worker Dispatcher，不增加第二条Transport状态机。
Correlation
合法SYSTEM Result完成当前target；timeout、shutdown与Result精确竞争。槽位占用立即拒绝，提交结果未知则返回unobserved。
BEST EFFORT

明确不承诺

  • 不创建Task或TaskItem
  • 不进入Result Routing
  • 不创建独立可靠Command或Result存储
  • 不提供结果查询与可靠重试
  • 不提供pause、drain、互斥或抢占
  • 不允许Server从候选Worker中选择目标

DIRECT_CALL只保证投递时不覆盖已有Worker槽位；已经消费的Direct Command不会被后来的TASK撤回。解绑、迁移、排他维护或可靠执行需要另行定义明确的Owner与机制。

04 · Transport substrate

共同机制，完整物理owner

Adapter和Worker都采用三层owner。统一发生在稳定机制合同上；WebSocket、line Socket、 OkHttp与Android HandlerThread仍由具体物理实现完整拥有。

NETTY ADAPTER

三层冻结结构

AggregateAdapter lifecycle、Process Manager和network shutdown ordering。
ConnectionInbound callback adapter、identity、first verification、route registry、Command routing与Result ingress。
Physical Server完整WebSocket或line-Socket listener、EventLoop、全部Channel、framing、write与close。
WORKER CORE

三层运行结构

Client具体网络、透明重连和物理callback serialization。
Transportidentity、Command decode、同步handler execution、Result encode与endpoint termination。
Run Controller只拥有显式run的RUNNING/STOPPED与一次Preparation；active stop先撤销run，endpoint耗尽后必须由Host再次start。
PREPARE & IDENTITY

Server拥有注册坐标

普通Worker使用CLIENT_KEY；Scenario使用SCENARIO_LAB inventory坐标。单条与1..100批量Prepare进入同一Identity、Binding与canonical Properties owner链，不构成跨Owner事务。HTTP中单标量、单集合和单Map直接作为JSON body；只有组合契约与结构化资源保留命名DTO。

JAVA HOST

显式启动，共享平台资源

Manager固定一个WorkerGroup与replica集合；透明重连复用已Prepare坐标，不刷新Properties。WebSocket reader与OkHttp TaskRunner使用Platform-owned virtual threads。

SCENARIO LAB

Mutation source，不是真相源

JSONL保存Lab坐标与Properties，不保存workerId。start、stop、原子文件替换和checkpoint只建立本地动作，不能替代Adapter Route或Kernel Scheduling观察。

DeliveryCommand
  targetAddress outside DTO
  src + dst + messageType + deadline + payload + opaque forward

Adapter
  WORKER target  -> current verified Channel -> physical write
  ADAPTER target -> fixed local handler

Worker
  full messageType Event Name -> immutable Definition -> resolver -> handler
  src -> invocation evidence only

DeliveryReport
  producer src + sourceId + destination + outcome + opaque payload/forward

05 · Runtime topology

一套 Java Kernel
两个稳定性层级

kernel_jvm拥有稳定的机械Owner与Redis转换， kernel_pacer_jvm拥有变化更快的Policy、Convergence与线程生命周期； Server只完成Spring装配和公开API。

DOC / KERNEL

Authority index

Java Kernel总入口连接mechanical Owner、Pacer Policy、跨模块边界和对应proof，不复制第二份运行机制。

KERNEL_JVM

Mechanical owners

稳定的Java 21 owner contracts、Redis providers、Candidate Cache与codec；不拥有调度策略、Pacer线程或Spring生命周期。

KERNEL_PACER_JVM

Policy & lifecycle

KernelPacerRuntime是唯一公开生产入口，固定装配Result Convergence与Dispatch Convergence。

SERVER_JVM

API & Spring assembly

选择受检Pacer Preset、装配mechanical owners，并把一个KernelPacerRuntime委托给Spring生命周期；不解释调度策略或装配单个Pacer。

TRANSPORT

Delivery mechanisms

Java 11 contract/Core、Netty Adapter、Java Worker与Android Worker，不依赖Kernel调度实现。

ASSEMBLY & OBSERVATION

Finite edges

Scenario/Android提供具体Definitions与Host；四个Integration与Frontend只通过公开API执行correctness、convergence、capacity、Android和有限诊断，不拥有Kernel truth。

06 · Proof & stability

固定claim，分层证明

每个机制claim只有一个Primary Proof；其他lane只能提供前置条件或边界见证。 完美正确性、故障收敛、连接容量与Android进程事实不能互相替代。

STABLE CUT

稳定owner cut

  • Task、TaskItem、Worker三条独立score轴
  • 两类Worker acquisition workflow与同一Matcher
  • 一个KernelPacerRuntime、两个Convergence Application
  • Kernel / Server / Transport authority
  • Adapter与Worker三层结构
  • Server发行包与Worker Host/SDK独立
EVOLVING

Owner-local增量

  • 有明确生产caller的mechanical operation

Owner & Boundary

JVM Contracts固定Owner算法与架构；Redis Owner证明原子转换；Runtime Boundary证明相邻Owner和协议拓扑。

Worker Correctness

2 Groups × 10 Workers、100 Items全部成功，并闭合Identity、Route、Extension、Result与Host restart。

Convergence Health

2 Groups × 50 Workers、1000 offered Items；固定mutation与named witnesses，不把所有offered work声明为成功。

Worker Capacity

10,000 offered WebSocket Workers、至少9,900 connected + HOT，并检查Server restart和native resource边界。

Android Worker Proof

API 33单App正确性与进程丢失恢复，加三App同Group的局部故障隔离；Android不是Java Worker的重复见证。

Finite Product Lanes

Android Host、Frontend、Runtime Distribution与Docs各自证明SDK、构建、发布或文档合同，不扩大运行时claim。
