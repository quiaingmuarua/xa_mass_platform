Project overview · 从任务到执行

XA Mass
架构全景

将一批工作拆成任务项，交给可用的 Worker 执行，再收集处理结果。 XA Mass 负责资源调度与执行推进，业务能力运行在独立的 Java 或 Android 终端上。

从一个任务开始 → 查看部署方式 打开文档目录 ↗

当前规模模型：少量活跃 Task · 每个 Task 大量任务项 · 有限 WorkerGroup 内大量 Worker

01 · 职责分工

四个部分，各自负责什么

一次任务执行需要接收请求、判断可用资源、解释匹配条件和调用业务能力。 这些职责分开维护，通过明确的接口协作。

KERNEL

决定与推进任务

维护任务和 Worker 的调度状态，决定分配、领取、重试、恢复与最终状态。

MATCHING

解释事实与条件

维护 Worker 属性与匹配规则，从 Kernel 提供的有限 Worker 集合中过滤候选。

SERVER

接收请求与协调

提供 API，校验请求、建立身份与绑定，将指令和反馈交给对应的负责模块。

TRANSPORT

连接、投递与执行

Adapter 将指令送达当前连接；Worker 调用已装配的本地能力并返回执行反馈。

阅读时会遇到的对象：Task 组织一批工作；TaskItem 是其中一个执行单元； Worker 是执行端；WorkerGroup 将 Worker 组织在同一个调度范围内。 下文沿着一项工作，看这四个部分如何接力。

02 · 任务主线

一个任务，怎样走到结果

以批量规范化电话号码为例：整批工作放在一个 Task 中，每条号码对应一个 TaskItem， 由装有号码处理能力的 Worker 执行。

01 / 提交工作
调用方通过 API 提交任务和输入，每个任务项指定要调用的能力及参数。 Server 完成校验与记录，Kernel 按任务类型推进初始化和调度。
02 / 获取资源
Kernel 获取候选 Worker，确认资源占用并领取任务项，形成目标确定的执行指令。 Worker 的获取方式由下方两条路径决定。
03 / 投递与执行
指令经 Server 和 Adapter 交给 Worker。Worker 按完整事件名找到本地处理器， 执行号码转换并返回反馈；投递环节沿用 Kernel 已确定的目标。
04 / 处理反馈
Server 将任务反馈路由给 Kernel。成功反馈用于记录结果并请求成功终态； 未完成工作由 Kernel 依据领取期限、重试预算和任务项期限继续推进或结束。 调用方通过 API 读取已观察到的结果。
PRECOMPUTED

按属性条件匹配

Kernel 先持有一个有限 Worker 池，Matching 用任务规则过滤出候选。 最终分配前，Kernel 仍要再次确认资源有效。

ON_DEMAND

按身份范围获取

任务项提供明确的 Worker ID 列表，或用空列表（ANY）让 Kernel 在所属分组内获取可用 Worker。这条路径不解释属性条件，也不使用预计算候选缓存。

结果与最终状态分别维护。成功结果的保存与任务项终态更新是先后进行的操作， 中间存在失败窗口；读到结果并不证明终态已完成。指令和反馈可能丢失或重复， 资源到期恢复也不会重建已经丢失的结果。 查看结果与状态的完整边界 ↗

03 · 直接调用

已经知道目标时，直接发起调用

除了提交任务，调用方也可以对指定 Worker 或 Adapter 发起 DIRECT_CALL， 例如查询已装配能力、读取快照或调试一次本地操作。

DIRECT_CALL

由调用方选择目标

指定目标选择 Adapter，再指定 Worker 或 Adapter 本地事件。
复用投递Server 校验请求，通过已有连接和本地能力完成调用。
有限等待Server 关联本次回复；等待超时仅表示没有观察到回复。
选择调用方式

任务推进，还是一次定向操作

需要资源选择、任务进度和调度重试时，使用 TASK 路径。

已知目标、希望立即查询或调试时，使用 DIRECT_CALL。它采用尽力交付，不提供可靠重试或持久结果查询。

一次调用成功，只说明这次操作获得了回复；不能据此判断该 Worker 当前是否可被调度。

DIRECT_CALL 不创建 TaskItem，也不取得 Kernel 调度租约，因此不提供暂停、排空、互斥或抢占。 尚未消费的 Worker 直接调用还可能被 TASK 指令替换。 调用准入与结果关联详见 Server 文档 ↗

04 · Worker 接入

让业务能力成为可调用的 Worker

Worker 运行在独立的宿主应用（Host）中。Host 选择 Java 或 Android SDK， 装配业务处理器，并显式管理 Worker 的启动和停止。

01 / 装配能力
Host 在启动前注册完整事件名与处理器，提供 Worker 的属性。 业务能力负责本地处理，SDK 负责协议、网络与运行生命周期。
02 / 准备身份
显式启动通过 Prepare 向 Server 提交注册坐标，取得稳定的 Worker ID 和连接地址，并建立绑定及最小 Worker 资源。Prepare 不保存匹配属性。
03 / 连接与运行
Worker 连接 Adapter，完成身份验证后接收指令。临时断线由客户端在当前运行内重连， 不重新 Prepare；运行终止后，由 Host 决定是否再次显式启动。
JAVA / ANDROID

共享协议，各自管理平台资源

Java 与 Android 共用 Worker Core 和投递协议，分别管理各自的网络与线程资源。 业务 Host 装配具体能力，Server 不创建或启动这些执行端。

WORKER PROPERTIES

通过连接上报匹配属性

首次与后续属性均由 Adapter 观察，经 Server 校验后写入 Matching， 无需重新 Prepare。首次属性到达前，身份可以存在，按属性匹配仍需等待。 上报采用尽力交付；已有候选不会因此撤销，也不直接改变调度状态。

连接、能力与调度可用性需要分别观察。Adapter 报告当前连接， Worker 报告实际装配的能力，Kernel 维护调度状态。WorkerGroup 中登记的事件名只是目录信息， 不能代替 Worker 已加载处理器的证据。 查看 SDK 与投递模块 ↗

05 · 运行部署

服务端集中装配，执行端独立运行

Server 将平台 API、调度、匹配消费和 Adapter 装配在同一个 Java 进程中。 SMS 作为业务模块按 profile 启用，使用现有服务提交任务、读取结果。 产品前端独立构建并由同一 Server 提供；Worker Host 独立运行。 

运行环境
├─ Server 进程（distribution/server 启动）
│  ├─ server_jvm：平台 API + 应用服务
│  ├─ SMS 模块 + /sms 页面（按 profile 启用）
│  ├─ Kernel：机械契约 + Pacer
│  ├─ Worker Matching
│  └─ 配置的 Adapter
├─ 外部 Redis
└─ 独立 Worker Host
   └─ Java / Android SDK + 业务能力
KERNEL 的两个模块

机制与策略分别维护

kernel_jvm 维护稳定的调度契约、资源与 Redis 操作。

kernel_pacer_jvm 维护调度策略、结果处理和持续推进它们的生命周期。

Server 装配这些模块和 Matching。每个 scope 只有一个启用 Pacer 的宿主；SMS 复用同一套应用服务和资源。

SERVER RUNTIME

运行服务端

发行包包含 Server、调度与匹配组件、Adapter 和编译后的前端。启动需要 Java 21 和外部 Redis。

WORKER SDK

接入业务执行端

将 SDK 接入自己的 Java 或 Android Host，装配所需能力。下游 AgentForge 通过发行包和公开 API 接入。

SCENARIO LAB

在本地建立实验环境

Scenario Host 共用一套 Java Worker 管理与本地控制台，运行 Lab 实验或 SMS 模拟号码。Host 独立于 Server 启动，随 SMS 预览包提供。

同一 Redis scope 只允许一个 Server 启用 Pacer，目前没有分布式主节点选举。 前端通过 API 观察和操作实际 Runtime；公开演示站使用 Mock 数据。 查看运行要求与启动方式 ↗

06 · 验证与文档

验证结果，分别能说明什么

读懂运行方式后，还需要知道哪些行为有对应证据。每条验证路径回答一个明确问题， 其适用范围由场景和观察方式决定，而非单看测试数量或 Worker 规模。

OWNER TESTS

局部规则是否成立

聚焦模块算法、合法状态转换与并发约束。真实 Redis 测试验证需要存储原子性的操作。

RUNTIME BOUNDARY

相邻模块能否正确交接

验证 API、编码、存储和投递边界在实际装配中的关系，覆盖局部测试无法说明的接口协作。

WORKER CORRECTNESS

理想环境能否完整执行

闭合身份、路由、能力、结果及 Host 重启关系，要求固定工作负载获得精确成功结果。

CONVERGENCE HEALTH

故障后能否恢复指定行为

先建立明确的本地故障，再独立观察连接、调度和指定任务的恢复，不要求全部提交项成功。

LOADED RECOVERY

持续负载下资源是否稳定

在持续工作和多次 Server 重启中验证任务完成、结果导出与资源边界，不扩展为吞吐或延迟承诺。

ANDROID WORKER

真实平台生命周期是否成立

验证 Android 进程丢失恢复与固定多应用间的故障隔离，保留平台特有的验证边界。

完整场景、明确不覆盖的行为与主要证明归属，见 Proof Registry。 SDK 构建、前端构建、发行包和文档检查各有独立验证；这些检查通过，不等于运行时场景已通过。
