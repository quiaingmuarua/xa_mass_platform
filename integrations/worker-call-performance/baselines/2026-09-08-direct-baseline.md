# 2026-09-08：1,000 Worker DIRECT_CALL 性能

**结论：在这次同机、短 Handler、30 秒的测量中，DIRECT_CALL 支持了
1,000 次/秒的成功调用，30,000 次请求全部成功且均在计划到达后的 1 秒内返回；
成功调用 p50 为 17.44ms，p95 为 76.36ms，p99 为 130.85ms。**
这是承载 Sekiro 类似远程能力调用场景的正面证据。它不构成长期 SLA，也没有
测出服务端容量上限。2,000/s 和 5,000/s 的调用体验明显退化，同时压测端调度
也受限，不能用这些档位的完成量给服务端容量定值。

## 测量版本与条件

- [正式 CI 运行](https://github.com/quiaingmuarua/xa_mass_platform/actions/runs/34215509498)：
  五个案例全部满足测量契约，工作区干净。
- Harness / runner：`c7b64c0850c162e0c4e96c2bb11b893b8586f773`。
  生产代码与 main `6f49c6a0232d86947751cc055d923f1a36ebe1e9` 相同。

  Server、Host、Harness 和 Redis 共用一台 CI 主机。
- 一个 Group、一个 WebSocket Adapter、1,000 个 Worker 实例。
  Scenario Host 在一个 JVM 中维护 1,000 条真实 Worker 连接，不是 1,000 台物理设备。
- 调用方轮转指定已知 Worker，每个 HTTP 请求只调用一个 Worker；使用现有
  MD5 Handler 和固定 64 字节输入，不提交 Task Items 或后台任务。
- 每个案例使用新 Server、Host、Redis 容器和 scope；预热 100/s、20 秒，
  每个 Worker 预热两次并全部成功。测量 30 秒，启动和准备不计入性能。
- DEFAULT Pacer 和既有 Adapter 配置；Direct 等待 1 秒、HTTP 客户端超时 5 秒，

  不计入下表，也不与正式数据合并。

## QPS 与响应体验

“成功 QPS”是本轮请求最终在原 HTTP 响应中成功的数量除以 30 秒，其中包含
测量窗口之后才返回的本轮响应；窗口内实际收到的成功响应速率另列，避免把
请求到达速率、响应速率和完成比例混为一谈。p99 仅包含成功样本，并从计划
到达时刻计时，包含压测端调度延迟。

| 目标 QPS | 发出 / 计划 | 成功 QPS | 窗口内成功响应/s | 原响应成功率 | 1 秒内成功率（占发出） | 成功 p99 | 判断 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | 3,000 / 3,000 | 100.00 | 99.97 | 100% | 100% | 108.33ms | 此负载点通过；仍有百毫秒级尾延迟 |
| 500 | 15,000 / 15,000 | 500.00 | 498.87 | 100% | 100% | 123.55ms | 此负载点表现完整 |
| 1,000 | 30,000 / 30,000 | 1,000.00 | 999.83 | 100% | 100% | 130.85ms | 本轮最高的完整、未受压测端限制的负载点 |
| 2,000 | 60,000 / 60,000 | 1,172.27 | 1,168.23 | 58.61% | 56.28% | 1,287.86ms | 显著退化，同时压测端受限 |
| 5,000 | 82,202 / 150,000 | 69.17 | 65.30 | 2.52% | 0.57% | 4,238.15ms | 严重退化，同时压测端受限 |

在 1,000/s 下，没有槽位拒绝、Direct 超时、未知提交、未发出或协议错误。
这比仅证明 HTTP 200 或最终可补查到结果更直接：30,000 次调用都在原响应里
给出了校验正确的 MD5 结果。但每档只有一次 30 秒测量，不能称为长时间稳定容量。

2,000/s 没有未发出的请求，但计划发送到实际发送的 p99 已达 222.94ms，超过
固定 100ms 压测端界限；5,000/s 为 700.17ms，并有 67,798 次未发出。
两个案例都保留诊断价值，但不建立服务端容量结论。特别是 1,172.27/s 不能
解读成“服务端上限为 1,172 QPS”。1,000～2,000/s 之间尚未定位。

## 高压下发生了什么

| 目标 QPS | 成功结果 | 槽位占用拒绝 | Direct 超时 | 提交/传输结果不确定 | 未发出 |
| --- | --- | --- | --- | --- | --- |
| 100 | 3,000 | 0 | 0 | 0 | 0 |
| 500 | 15,000 | 0 | 0 | 0 | 0 |
| 1,000 | 30,000 | 0 | 0 | 0 | 0 |
| 2,000 | 35,168 | 20,567 | 4,265 | 0 | 0 |
| 5,000 | 2,075 | 75,749 | 4,154 | 224 | 67,798 |

本轮没有 HTTP 429、协议错误或 observed 非成功结果。高压损失主要表现为
`command-slot-occupied` 和 `timeout`，并非已观察到的 MD5 Handler 报错。
这说明后续应调查请求入口、命令投递和结果返回的排队/竞争；本轮尚未隔离
具体内部瓶颈，也不能由拒绝状态推断占用槽位内 Command 的执行历史。

DIRECT_CALL 的 HTTP 200 可以携带拒绝或未观察到结果，因此不叫“HTTP 接受成功率”。
Direct 超时结束等待，不撤回已投递 Command，也不证明业务执行失败。
它没有 Task Result 的持久化补查接口。8,419 个超时和 224 个不确定样本保持
执行未闭合，安全关联记录存入 [压缩样本](2026-09-08-direct-unclosed.jsonl.gz)，
共 8,643 条；不转成业务失败或成功。

## 资源与成本

1,000/s 测量窗口内：

| 进程 | 平均使用 CPU 核数 | 峰值 RSS |
| --- | --- | --- |
| Server（含 Adapter） | 2.21 | 643.77 MiB |
| Worker Host | 0.22 | 337.82 MiB |
| Harness | 0.71 | 306.86 MiB |
| Redis | 0.18 | 16.74 MiB |

Server 和发压端消耗了较多 CPU，且它们共用 4 个逻辑 CPU。Worker 的 MD5
计算消耗较低。由此优先调查调用处理与投递开销是合理方向，但这些聚合数据
不能独立证明某个 Owner、线程或 Redis 命令是瓶颈。

五个案例全阶段采样峰值：Server 253 原生线程 / 5,159 FD，Host 46 / 1,027，
Harness 27 / 4,109，均未超过本 lane 的 512 / 8,192 界限。
Redis INFO 是聚合诊断，包含 Lua 内部命令，不能作为客户端往返次数。

## 如何用于产品判断

- 对已有 Java/Android Worker、调用方能指定设备的远程能力调用，这次结果支持
  继续用 DIRECT_CALL 做真实业务验证。1,000/s 档的同步返回体验是正面证据。
- 当前低负载仍存在约 100ms 的尾延迟；如果业务要求个位数毫秒或非常严格的
  截止时间，报告不支持这类承诺。
- 本轮没有后台 Task，也没有同时使用 TASK 与 DIRECT_CALL。TASK 可覆盖尚未
  消费的 Direct Command，Direct 不提供调度排他或持久化恢复，所以不能把
  本轮结果外推为在线与后台混合时的吞吐或可靠性。
- 与上一份 Task Call 基线相比，调用路径和 Worker 数都不同，且运行在不同
  CI 主机上。这些数字不构成隔离变量的性能对照，不计算“快了多少倍”。
- 没有运行 Sekiro 的相同配置基准，也没有跨机、移动网络、真实业务 Handler
  或长期运行测量。当前证据说明该衍生场景可行，不等于完整产品或容量对标完成。

下一步若要找容量边界，应先处理高压档位的发压限制，再对 1,000～2,000/s
区间和重复运行采样，定位入口、命令消费与结果返回耗时。Worker 数仍固定
1,000，沿用性能 lane 的独立 claim，不再用不同 Worker 数重复正确性证明。
