# 任务执行流

最后核对：2026-04-13

本文档只描述当前主线代码真实在跑的路径，不描述历史 v2 试验设计。

## 1. 当前已实现主线

### 1.1 创建任务

入口：

- `POST /status/api/tasks`
- `TaskApiController.createTask()`
- `TaskManager.createTask(dto)`

当前行为：

1. 生成 `tid`
2. 创建 `Task`，初始状态为 `NEW`
3. 将任务写入 `TaskStorage`
4. 遍历 `targetList`
5. 每个 target 生成一条持久化 `TaskMsg`
   - 独立 `msgId`
   - 绑定 `taskId`
   - `target` 保存真实目标值

当前约束：

- `targetList = null` 时安全，不抛 NPE
- `taskInitNumber` 会按 target 数量累计

### 1.2 状态机

```text
NEW -> READY -> PAUSED -> READY
NEW -> BLOCKED -> READY
READY/RUNNING -> PAUSED
any non-TERMINAL -> TERMINAL
NEW/TERMINAL -> delete
```

当前由 `TaskStatus.canTransitionTo(...)` 和 `TaskManager` 生命周期方法共同约束：

| 方法 | 允许初始状态 | 目标状态 |
|------|--------------|----------|
| `approveTask` | `NEW`, `BLOCKED` | `READY` |
| `rejectTask` | `NEW` | `BLOCKED` |
| `pauseTask` | `READY`, `RUNNING` | `PAUSED` |
| `resumeTask` | `PAUSED` | `READY` |
| `cancelTask` | 任意非 `TERMINAL` | `TERMINAL` |
| `deleteTask` | `NEW`, `TERMINAL` | 物理删除 |

### 1.3 READY 到 RUNNING

当前不是 UI 驱动，而是 engine 主线驱动：

1. 任务通过审核或恢复后进入 `READY`
2. `TaskManager` 通知 READY listeners
3. `MassEngine` 注册了 `TaskAssignWorker`
4. `MassEngine` 会：
   - 启动时提交已有 `READY` 任务
   - 在 `approveTask()` / `resumeTask()` 后提交新的 `READY` 任务
5. `TaskDeviceAssignListener` 按国家、规则、设备锁做匹配
6. 匹配成功时：
   - 更新 `scheduleDeviceCnt`
   - 将任务从 `READY` 转为 `RUNNING`

注意：

- `TaskAssignWorker` 现在不再依赖 `mockMode=true` 才启动

### 1.4 TaskMsg 分配与下发

当前主线已经不是“临时生成 pushQueue 后停在内存里”。

真实路径：

1. `TaskManager.createTask()` 已经创建并持久化 `TaskMsg`
2. `SimpleTaskMsgAssignListener` 从 `TaskStorage` 读取这些持久化 `TaskMsg`
3. 只处理当前还处于 `INIT` 的消息
4. 对每条消息执行：
   - 绑定 `deviceId`
   - 绑定 `tokenId`
   - 绑定 `batchId`
   - 状态推进到 `SENT`
5. `GatewayTaskMsgPublisher` 将消息转成 `TASK/step`
6. 通过 gateway output transporter 发到 WebSocket 下行

这意味着：

- 下发消息与持久化消息的 `msgId` 已经统一
- 回执可以按 `taskId + msgId` 回写，不再存在“两套消息主键”

### 1.5 客户端回执与进度收敛

当前已实现的入站路径：

1. 客户端上行 `TASK/step`
2. gateway 根据 `MessageHandlerRegistry` 命中 `GatewayTaskResultHandler`
3. handler 调用 `TaskManager.handleTaskMessageResult(taskId, msgId, success, detail)`
4. `TaskManager` 更新对应 `TaskMsg`
5. `TaskManager.updateTaskProgress(taskId)` 重新统计：
   - `taskExecutedNumber`
   - `taskUnExecutedNumber`
6. 当任务处于 `RUNNING` 且全部 `TaskMsg` 已进入终态时：
   - 任务自动收敛到 `TERMINAL`

当前支持的结果写回：

- `SUCCESS`
- `FAILED`

mock 客户端当前已同步：

- 回执 `project`
- 回执 `response=true`
- 回执 `TASK/step`

## 2. 当前仍未完成的部分

### 2.1 调度器批量接口

`SimpleTaskScheduler.scheduleTasks()` 仍然返回空列表。

现状说明：

- 这是遗留 stub
- 但当前主线 `READY -> RUNNING` 已不依赖它

### 2.2 关闭流程

应用退出有时仍需要两次 Ctrl-C。

现状说明：

- `TaskAssignWorker.stop()` 已做 `shutdownNow() + awaitTermination`
- 但整个应用关闭链路还没有完全收敛

### 2.3 EventBus 收敛

运行时仍存在 `old.eventbus` 路径，尚未统一到目标实现。

### 2.4 非 MEMORY 存储

Redis / Database 仍未实现，只保持 fail-fast。

## 3. 当前推荐验证顺序

1. API 创建任务
2. API 审核任务
3. 检查任务是否进入 `RUNNING`
4. 观察 WebSocket 是否收到 `TASK/step`
5. 检查客户端回执后 `TaskMsg` 和 `Task` 是否收敛
6. 最后再回到页面验证同一条链路
