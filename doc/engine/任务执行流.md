# 任务执行流

最后更新：2026-04-13

本文档只描述当前主线代码已经验证过的执行路径，不描述历史 `v2` 设想。

## 1. 生命周期

当前状态机：

```text
NEW -> READY -> PAUSED -> READY
NEW -> BLOCKED -> READY
READY -> RUNNING -> TERMINAL
READY/RUNNING -> PAUSED
any non-TERMINAL -> TERMINAL
NEW/TERMINAL -> delete
```

状态约束：

| Action | Allowed From | Target |
| --- | --- | --- |
| `approveTask` | `NEW`, `BLOCKED` | `READY` |
| `rejectTask` | `NEW` | `BLOCKED` |
| `pauseTask` | `READY`, `RUNNING` | `PAUSED` |
| `resumeTask` | `PAUSED` | `READY` |
| `cancelTask` | 任意非 `TERMINAL` | `TERMINAL` |
| `deleteTask` | `NEW`, `TERMINAL` | 物理删除 |

## 2. READY 到 RUNNING

当前真实代码路径：

1. 任务通过审核或恢复后进入 `READY`
2. `TaskManager` 通知 READY listeners
3. `MassEngine` 中的 `TaskAssignWorker` 接手分配
4. `TaskDeviceAssignListener` 执行设备匹配
5. 匹配成功后：
   - 写入 `scheduleDeviceCnt`
   - 将任务从 `READY` 转成 `RUNNING`
6. `SimpleTaskMsgAssignListener` 复用持久化 `TaskMsg`
7. 每条消息绑定：
   - `deviceId`
   - `tokenId`
   - `batchId`
   - 状态推进到 `SENT`
8. `GatewayTaskMsgPublisher` 将消息下发为 `TASK/step`

关键实现事实：

- `TaskAssignWorker` 不再依赖 `mockMode=true`
- `MassEngine` 会在启动时补提已有 `READY` 任务
- `approveTask()` / `resumeTask()` 都会触发 READY 事件

## 3. Mock 数据如何满足分配前置条件

`MassApplication.loadMockData(...)` 现在会在 mock/dev 启动时补齐分配条件：

- 归一化设备 `supportedProjects` 为 `Project` 枚举
- 为缺少 token 的设备自动生成 `LOGIN_READY` token

这个修复解决了此前“API 审核后停在 `READY`”的问题。根因不是 worker 没跑，而是 mock 设备不满足默认规则里的 `supportsProject` 和 token 条件。

## 4. RUNNING 到结果回写

当前真实代码路径：

1. 默认 `dev` 启动在 `ApplicationReadyEvent` 后自动拉起 mock WebSocket clients
2. mock client 收到 `TASK/step`
3. mock client 回传 `TASK/step` 结果
4. `GatewayTaskResultHandler` 调用 `TaskManager.handleTaskMessageResult(...)`
5. `TaskManager` 根据 `taskId + msgId` 更新持久化 `TaskMsg`
6. `TaskMsg` 进入：
   - `SUCCESS`
   - `FAILED`
7. 当任务处于 `RUNNING` 且全部 `TaskMsg` 都进入终态时：
   - 任务自动收敛为 `TERMINAL`

## 5. 2026-04-13 真实 API smoke 结果

已确认：

- `POST /status/api/tasks` 创建后状态为 `NEW`
- `POST /status/api/tasks/{taskId}/audit?approved=true` 后，任务会经过 `RUNNING` 并自动收敛到 `TERMINAL`
- `GET /status/api/tasks/{taskId}/messages` 可观察到消息进入 `SUCCESS`
- `deviceId` / `tokenId` / `batchId` 会写回持久化 `TaskMsg`
- `scheduleDeviceCnt` 和 `taskExecutedNumber` 会按真实执行结果更新
