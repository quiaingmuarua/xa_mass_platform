1. createTask(TaskCreateRequestDto dto)
   用户发起任务创建（通常会有任务类型、备注、预期目标等）。

数据库生成一条 Task 记录，status=INIT，并生成唯一 taskId（如 tid）。

2. uploadTaskSeed(String tid) // 流式多次调用
   用户分批上传 seed 文件/数据（百万级用流式最合理）。

每次上传：服务端解析/批量入库（可用 insert ignore 或分区表优化），写入 seed 表，附带 tid、原始值、状态等字段。

支持多次上传/断点续传，直到用户/前端标记“上传完成”。

3. 等待审核（可选，自动/人工）
   某些业务需要审核，Task.status 进入 WAIT_AUDIT。

审核通过，Task.status → READY。

自动化场景可跳过，直接进入 READY。

4. Device-Task绑定（可选）
   部分场景任务需要提前绑定可用设备（比如做 AB 实验、特殊分配）。

普通抓取/群发等场景，可以“到调度时动态分配设备”，无需预先绑定。

商用建议：Device 状态和 Pool 可以做成池化服务、动态调度。

5. 判定是否可执行/满足触发条件
   通常要求达到最低设备数量、任务在 READY 状态。

如设备不足，不能调度，否则可能导致任务堆积、延迟。

6. 生成 TaskMsg（genTaskMsg）
   核心步骤！

系统调度服务按配置/策略（如每台设备每批 100 seeds），从seed表中选取“待执行”状态的seed，批量生成 TaskMsg。

每个 TaskMsg 记录：msgId、tid、deviceId、seedList（或 seedRange）、分配时间、状态等。

对应 seed 也标记已分配给哪个 TaskMsg（可以在 seed 表增加 lastMsgId 字段便于追踪）。

7. 推送到执行队列（push_gateway_task_queue）
   每个 TaskMsg 作为独立“消息”，推入任务执行队列（通常基于 Redis、Kafka 或自定义 MQ）。

Gateway/Executor 从队列拉取 TaskMsg，下发到设备/客户端。

8. 客户端拉取、执行、结果回传
   设备从 Gateway 拉取自己的 TaskMsg，处理 seed 列表。

执行完毕后，逐条/批量回传 seed 结果，系统更新 seed、TaskMsg 状态。

Task 根据所有 seed 的完成进度统计总进度和最终状态。
